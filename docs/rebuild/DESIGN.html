1. Purpose and target users

Nuroli supports a personal learning loop: ask a model a question, research facts with visible sources, keep going deeper, turn what was worked out into a reviewed summary, keep that summary as knowledge, and ask questions across saved knowledge later. R-01

Target users. People who learn by questioning: engineers, researchers, students, and self-taught professionals who want their conclusions kept separately from the messy conversations that produced them. They install Nuroli themselves or use an installation someone runs for a small group. Each user's data is private to them. R-01

Operator. The person who installs and configures Nuroli. The operator chooses the model endpoint and search key, and decides whether registration is open. The operator is not a special user inside the product. R-14

Three kinds of content, always distinguishable. Conversations (working material, unconfirmed), drafts (unconfirmed summaries, marked in blaze ochre), and saved knowledge (confirmed summaries, marked in trail green). Web evidence is a fourth kind, marked in slate blue and never presented as knowledge. This colour semantics is the backbone of the interface.

2. Design principles

  1. The next useful action is always visible. A new user sees one composer and one instruction. A returning user sees their last conversation and their library count.
  2. Nothing is saved as knowledge without the user saying so. The confirm button is the only path into the library, and it always shows what it will save. R-18
  3. Work is never lost by navigation. Composer text and draft edits survive route changes and reloads. Cancel keeps the draft; discard is a separate, labelled action.
  4. Honest states. Streaming, stopped, failed, skipped research, and insufficient evidence are each shown with an icon and a word, never colour alone.
  5. Reading first. Assistant text uses the reading typeface at 68 characters measure. Controls stay quiet until hovered or focused.
  6. One model, shown plainly. The configured model's name appears on every reply and in the composer. No picker exists until multiple models exist. R-06

5. Installation, first run, and configuration behavior

The operator experience is the README plus two files. The product surfaces configuration only through what it enables or hides.

  1. Copy .env.example to .env and fill in: public origin, secret key, database password, model base URL, model name, model API key (optional for local runtimes), and optionally the search key, Google client id and secret, and the registration flag.
  2. Run docker compose up -d. The API applies migrations and starts. make check-model (or the equivalent command in the API container) sends a one-token request and prints success or the exact error. R-19
  3. Open the public origin. The first registered account becomes the admin. R-14
ConfigurationVisible effect in the product
Search key missing or provider noneThe research toggle is not rendered; the capabilities endpoint reports research unavailable; the Ask screen's "research this instead" action opens a conversation without the toggle. R-08
Google not configuredThe Google button is not rendered on entry screens.
Registration closedThe register form shows "Registration is closed on this installation" with the sign-in link; the register route still renders so the message is discoverable.
Model unavailableSending works up to the model call, then the reply shows a failed state with "The configured model did not respond" and a retry action. No configuration details are shown to users. R-06
Plain HTTP on a LAN addressNot supported by default. The README states that the session cookie requires HTTPS or localhost, and that NUROLI_SESSION_COOKIE_SECURE=false is an explicit, documented risk. R-13
Model nameShown in the composer footer and on every reply, as configured. Model name never reveals the base URL or key.

Operator commands (inside the API container): nuroli check-model, nuroli reset-password <email> (prints a temporary password once and revokes sessions R-15), nuroli delete-user <email>, plus make backup and make restore from the host.

8. The single configured model and future model selection

V1 has exactly one model, named by the operator. R-06 The name appears in the composer footer and in every assistant meta line, so the attribution rule is visible from day one. There is no picker, no model settings screen, and no per-user key entry.

Reserved behavior for later. When multiple models exist, the composer footer's model name becomes a menu that sets the model for the next reply only. Earlier replies keep their recorded model names. The conversation list and summaries do not change. This spec reserves the footer slot and the meta-line attribution so the later change is additive.

13. Account

Display name edit, change password (current, new, confirm; signs out other sessions), and sign out. Google-only accounts see "You sign in with Google" instead of the password form. There is no delete-account action in v1; the screen states that the operator can delete an account on request.

Target: WCAG 2.2 AA, checked with axe in end-to-end tests on every screen. R-27

17. Copy rules

  • Sentence case everywhere. No exclamation marks. No "oops".
  • Name the three content kinds consistently: conversation, draft, saved summary (in the library). Never "note", "document", or "memory".
  • Say what happened and what to do next in one sentence each: "The model took too long to answer. Retry or try a shorter question."
  • Never expose configuration values, hostnames, or keys in user-facing text.
  • Web evidence is always "sources" or "from the web"; saved knowledge is always "from your library" or "your saved summaries".
  • Destructive dialogs name the object and the consequence: "Discard this draft? Your saved summary, if any, is not affected."
